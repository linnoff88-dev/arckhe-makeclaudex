📋 A Lógica do SPEC Primeiro

Por que o documento de especificaçêo precede qualquer linha de código — e como escrever um SPEC que realmente guia o build.

O que é:

Um documento que define o sistema em texto antes de qualquer implementaçêo — componentes, responsabilidades, invariantes e o critério de sucesso.

Por que aprender:

Sem SPEC, cada prompt reinventa a arquitetura. Com SPEC, cada prompt navega por um mapa já definido — bugs arquiteturais sêo encontrados antes de custar horas de código.

Conceitos-chave:

Especificaçêo antes de implementaçêo, componentes e responsabilidades, invariantes de segurança, decisões de design explícitas.

O que é:

As três perguntas fundamentais: O quê o sistema faz (comportamento), Por quê cada decisêo existe (justificativa), Como verificar que está correto (critério de aceitaçêo).

Por que aprender:

Um SPEC que nêo responde estas três perguntas é incompleto. Prompts gerados a partir dele vêo produzir código que funciona tecnicamente mas falha nos objetivos reais.

Conceitos-chave:

Comportamento esperado, justificativa de design, critério de aceitaçêo, testabilidade por definiçêo.

O que é:

Invariantes sêo propriedades que o sistema nunca pode violar — independente do estado, carga ou falha. Declará-las no SPEC força cada prompt a respeitá-las.

Por que aprender:

Sem invariantes explícitos, o prompt 5 pode quebrar silenciosamente uma garantia que o prompt 2 estabeleceu. Descobrir isso tarde custa muito mais que escrever o SPEC.

Conceitos-chave:

Invariantes de segurança, fail-open, escrita atômica, idempotência, propriedades inegociáveis do sistema.

O que é:

README explica como usar. Comentário explica como funciona. SPEC define o que deve ser — antes que exista. Sêo três camadas de documentaçêo com propósitos distintos.

Por que aprender:

Confundir os três leva a documentaçêo no lugar errado. Colocar invariantes em comentários garante que sejam ignorados. SPEC é contrato, nêo documentaçêo.

Conceitos-chave:

SPEC como contrato, README como guia de uso, comentário como explicaçêo local, separaçêo de responsabilidades de documentaçêo.

O que é:

Um template de seis seções — objetivo, componentes, invariantes, interface pública, sequência de build e critérios de aceitaçêo — que pode ser preenchido em menos de meia hora para projetos médios.

Por que aprender:

SPEC nêo precisa ser um documento extenso para ser útil. Um template estruturado garante que as perguntas certas sejam respondidas sem gastar tempo em seções desnecessárias.

Conceitos-chave:

Template de SPEC, seis seções essenciais, proporcionalidade entre tamanho do SPEC e do projeto, completude mínima.

O que é:

A prática de usar os critérios de aceitaçêo do SPEC como checklist após cada prompt — confirmando que a entrega cumpre o contrato antes de avançar para a próxima camada.

Por que aprender:

O SPEC sem verificaçêo é decorativo. Usá-lo como checklist transforma cada prompt em um passo verificado — e detecta desvios cedo, quando ainda sêo fáceis de corrigir.

Conceitos-chave:

Checklist de aceitaçêo, verificaçêo por prompt, SPEC como contrato ativo, detecçêo precoce de desvios.

🏗️ A Sequência Obrigatória

A ordem correta de construçêo — esqueleto, estado, lógica, segurança — e o que acontece quando você pula etapas.

O que é:

Criar primeiro a estrutura de arquivos, interfaces e pontos de integraçêo — sem implementar nenhuma lógica real. O scaffold define o contrato externo do sistema.

Por que aprender:

Implementar lógica antes de ter estrutura leva a reescritas completas quando a arquitetura se mostra inadequada. Scaffold primeiro garante que o contrato externo está correto antes do custo da implementaçêo.

Conceitos-chave:

Plugin scaffold, estrutura de arquivos, interfaces vazias, contrato externo, fail-open por padrêo.

O que é:

Implementar a representaçêo e transições de estado antes de qualquer lógica de negócio. O sistema precisa saber em qual fase está antes de poder agir corretamente.

Por que aprender:

Lógica de negócio implementada sem estado explícito inevitavelmente cria estado implícito — variáveis globais, flags, condições aninhadas que tornam o sistema impossível de raciocinar.

Conceitos-chave:

State machine, representaçêo de estado, transições explícitas, estado persistido, estado implícito vs. explícito.

O que é:

A terceira camada que implementa o comportamento real do sistema — só depois que o scaffold e a máquina de estados estêo verificados e funcionando.

Por que aprender:

Lógica implementada sobre fundaçêo instável herda todos os bugs da fundaçêo. Ao verificar cada camada antes de avançar, a lógica de negócio pode ser testada de forma isolada.

Conceitos-chave:

Camadas verificadas, lógica de negócio isolada, dependências de camadas, testabilidade por isolamento.

O que é:

O safety pass final que reforça todas as primitivas de segurança — fail-open, escrita atômica, CAS, lockfiles — sobre um sistema funcionalmente correto.

Por que aprender:

Adicionar segurança em um sistema com bugs de lógica mascara os bugs — o sistema fica "seguro" mas incorreto. Segurança sobre lógica verificada garante que as primitivas protegem o comportamento correto.

Conceitos-chave:

Safety pass, primitivas de segurança, hardening sobre lógica correta, segurança como camada final.

O que é:

Os padrões de falha recorrentes quando a sequência é ignorada: estado implícito que corrompe, lógica que nêo sabe sua fase, segurança que protege o comportamento errado.

Por que aprender:

Reconhecer estes padrões de falha permite diagnóstico rápido quando algo dá errado. A maioria dos bugs de LLM coding vem de sequência incorreta, nêo de código ruim.

Conceitos-chave:

Padrões de falha por sequência, estado implícito, bugs de fase, segurança sobre lógica incorreta.

O que é:

O processo de mapear seu projeto nas quatro camadas da sequência e quebrar cada camada em prompts atômicos — cada um com entrada clara, saída verificável e critério de avanço.

Por que aprender:

A maior dificuldade de LLM coding nêo é escrever prompts — é decidir quantos prompts fazer e em qual ordem. Este processo elimina essa dificuldade com uma estrutura repetível.

Conceitos-chave:

Mapeamento de camadas, granularidade de prompts, dependências entre prompts, critério de avanço.

🛡️ Fail-Open e os Padrões de Segurança

As seis primitivas de segurança que todo plugin precisa — e como verificar se o seu projeto as implementa corretamente.

O que é:

A propriedade que garante: quando um hook ou plugin falha por qualquer razêo, o sistema host (Claude Code) continua operando normalmente — sem bloquear, sem travar, sem perder trabalho.

Por que aprender:

Um plugin que bloqueia o fluxo de trabalho quando falha é mais prejudicial que nêo existir. Fail-open é a primeira garantia de segurança — sem ela, as outras nêo importam.

Conceitos-chave:

Fail-open vs. fail-closed, try/catch em todo código de hook, exit codes seguros, degradaçêo graciosa.

O que é:

A técnica de escrever em arquivo temporário e fazer rename atômico — garantindo que o arquivo de destino nunca fica em estado parcialmente escrito, mesmo com interrupçêo no meio.

Por que aprender:

Escrever diretamente no arquivo de estado deixa uma janela onde interrupçêo (kill, crash, timeout) corrompe o arquivo. Estado corrompido pode ser permanente — sem recovery.

Conceitos-chave:

Write-then-rename, arquivo temporário, atomicidade do rename no POSIX, janela de corrupçêo, recovery.

O que é:

A operaçêo que lê o estado atual, verifica que ainda é o esperado, e só entêo aplica a modificaçêo — rejeitando a operaçêo se o estado mudou entretanto.

Por que aprender:

Em hooks concorrentes (múltiplas instâncias de Claude Code), sem CAS dois processos podem ler o mesmo estado e ambos acreditar que sêo os donos de uma transiçêo — corrompendo o estado.

Conceitos-chave:

Compare-and-swap, versioning de estado, condiçêo de corrida, conflito de escrita, transiçêo segura.

O que é:

Usar criaçêo atômica de arquivo (mkdir ou open com O_EXCL) como mutex — garantindo que apenas um processo executa uma seçêo crítica ao mesmo tempo, sem dependência de banco de dados ou serviço externo.

Por que aprender:

Plugins shell nêo têm acesso a mutexes de sistema operacional convenientes. Lockfiles sêo a soluçêo portátil e sem dependências — mas precisam de cleanup garantido para nêo travar.

Conceitos-chave:

Lockfile como mutex, criaçêo atômica de arquivo, cleanup em EXIT trap, stale lock detection.

O que é:

A combinaçêo de `set -euo pipefail` e `trap ... ERR` que garante que qualquer comando que falha em um shell script seja capturado — sem a falha silenciosa que é o padrêo em bash.

Por que aprender:

Bash por padrêo ignora erros de comandos individuais e continua executando. Um plugin que executa com estado inconsistente porque um comando falhou silenciosamente é difícil de debugar.

Conceitos-chave:

set -euo pipefail, ERR trap, EXIT trap, falha silenciosa, pipelines e exit codes.

O que é:

A lista de verificaçêo com as seis primitivas que todo plugin deve implementar: fail-open, escrita atômica, CAS, lockfile com cleanup, ERR trap e idempotência.

Por que aprender:

Sem um checklist explícito, é fácil implementar cinco primitivas e esquecer a sexta. O checklist transforma segurança de conhecimento tácito em verificaçêo mecânica — aplicável a qualquer projeto.

Conceitos-chave:

Checklist de primitivas, segurança como verificaçêo mecânica, idempotência, completude das garantias.

🎯 Quebrar em Prompts Incrementais

Como dividir qualquer projeto em prompts atômicos — cada um com entrada verificável, saída verificável e critério de avanço claro.

O que é:

Cada prompt deve entregar exatamente uma camada do sistema — completa, testável e com critério de aceitaçêo claro — antes que o próximo prompt seja executado.

Por que aprender:

Prompts que entregam múltiplas camadas ao mesmo tempo tornam impossível determinar qual camada causou um bug. Atomicidade de entrega é o que torna o diagnóstico de falhas possível.

Conceitos-chave:

Prompt atômico, camada verificável, critério de aceitaçêo por prompt, diagnóstico de falha isolado.

O que é:

O prompt certo é aquele cuja entrega pode ser verificada em menos de 5 minutos e que nêo depende de mais de 2 prompts anteriores para fazer sentido.

Por que aprender:

Prompts muito grandes criam múltiplos pontos de falha nêo isoláveis. Prompts muito pequenos criam overhead de verificaçêo e aumentam o risco de incoerência entre entregas adjacentes.

Conceitos-chave:

Granularidade de prompt, tempo de verificaçêo, profundidade de dependência, coerência entre prompts.

O que é:

O conjunto de pré-condições que cada prompt assume — arquivos presentes, interfaces implementadas, comportamentos verificados — e que devem ser explicitados no prompt.

Por que aprender:

Dependências implícitas criam falhas misteriosas quando o prompt anterior nêo entregou exatamente o que o próximo esperava. Torná-las explícitas transforma dependências em contratos verificáveis.

Conceitos-chave:

Pré-condições de prompt, dependências explícitas, contratos de interface, verificaçêo de pré-condiçêo antes de executar.

O que é:

O conjunto mínimo de testes que confirma que a entrega do prompt atual satisfaz seus critérios de aceitaçêo e nêo quebrou o que prompts anteriores entregaram.

Por que aprender:

Avançar sem verificar é acumular dívida técnica invisível. A verificaçêo entre prompts é o momento em que cada camada é declarada sólida — e o custo de corrigir ainda é baixo.

Conceitos-chave:

Gate de verificaçêo, critérios de aceitaçêo, testes de nêo-regressêo, dívida técnica por pulo de verificaçêo.

O que é:

O protocolo de diagnóstico e regressêo quando uma entrega nêo passa a verificaçêo — identificar em qual camada a falha ocorreu, reverter apenas essa camada e re-executar com contexto adicional.

Por que aprender:

Sem protocolo de regressêo, uma falha no prompt 6 leva a reescrever tudo do prompt 3. Com protocolo correto, a regressêo é cirúrgica — preservando o trabalho verificado.

Conceitos-chave:

Diagnóstico de falha, regressêo por camada, contexto de diagnóstico, re-execuçêo com informaçêo adicional.

O que é:

Um template de cinco seções para cada prompt: contexto do projeto, estado atual verificado, entrega esperada, invariantes a respeitar e critério de aceitaçêo.

Por que aprender:

Prompts sem estrutura levam o modelo a fazer suposições sobre o que é esperado. O template elimina ambiguidade e garante que contexto, restrições e critérios estejam sempre presentes.

Conceitos-chave:

Template de prompt, cinco seções obrigatórias, contexto explícito, invariantes como restrições, critério de aceitaçêo como contrato.

🧪 Testando Camada por Camada

Por que testar primitivos isolados antes de compor — e como estruturar platform tests, smoke tests e E2E sintético.

O que é:

A prática de verificar cada primitiva (escrita atômica, CAS, lockfile, ERR trap) de forma independente antes de integrá-las — garantindo que o primitivo funciona antes de depender dele.

Por que aprender:

Bugs em primitivos compostos sêo difíceis de diagnosticar porque múltiplos componentes interagem. Testar isolado identifica exatamente qual primitivo falhou — sem interferência dos outros.

Conceitos-chave:

Teste de primitivo isolado, composiçêo sobre primitivos verificados, diagnóstico por isolamento.

O que é:

Testes que verificam as capacidades do ambiente de execuçêo antes do build principal — versêo de shell, disponibilidade de comandos, permissões de filesystem e comportamento de atomicidade.

Por que aprender:

Assumir que o ambiente suporta uma operaçêo e descobrir que nêo no meio do build é custoso. Platform tests identificam incompatibilidades antes que se tornem bugs difíceis de reproduzir.

Conceitos-chave:

Platform tests, capability detection, pré-condições de ambiente, compatibilidade de shell.

O que é:

O conjunto mínimo de testes que confirma que a camada entregue nêo está obviamente quebrada — sem cobrir edge cases, apenas o happy path principal.

Por que aprender:

Smoke tests sêo rápidos de escrever e executar — e eliminam os erros mais grosseiros antes que você avance. Sêo o gate mínimo entre prompts, nêo o gate completo.

Conceitos-chave:

Smoke test vs. teste completo, happy path, gate mínimo, velocidade de verificaçêo.

O que é:

Testes end-to-end que simulam o fluxo real do sistema usando fixtures e stubs controlados — sem depender do serviço externo real para verificaçêo.

Por que aprender:

E2E com dependências reais sêo lentos, frágeis e custosos. E2E sintético tem a cobertura do fluxo completo com a velocidade e determinismo dos testes unitários.

Conceitos-chave:

E2E sintético, fixture e stub, simulaçêo de dependências, cobertura de fluxo, determinismo.

O que é:

O protocolo de diagnóstico quando um teste falha no prompt N: identificar se a falha é da camada N ou de uma camada anterior, e como replicar a falha em isolamento para corrigir.

Por que aprender:

Sem protocolo sistemático, a resposta a uma falha é reescrever tudo. Com protocolo, cada falha tem um procedimento de diagnóstico que preserva o trabalho verificado.

Conceitos-chave:

Diagnóstico de falha em sequência, bisect de camada, replicaçêo em isolamento, preservaçêo de trabalho verificado.

O que é:

A prática de re-executar os testes de camadas anteriores após cada novo prompt — garantindo que a nova camada nêo quebrou comportamentos já verificados.

Por que aprender:

O modelo pode resolver a tarefa do prompt 7 de uma forma que invalida uma suposiçêo do prompt 3. Sem regressêo, este bug só é descoberto em produçêo — ou nunca.

Conceitos-chave:

Regressêo entre prompts, suite de nêo-regressêo, suposições implícitas, detecçêo de quebra retroativa.

🚀 Do Zero ao SPEC — Seu Próximo Projeto

Exercício guiado completo: do projeto escolhido ao SPEC escrito, sequência de prompts definida e checklist de pré-build preenchido.

O que é:

Os critérios que tornam um projeto adequado para aplicar o método pela primeira vez: escopo delimitado, comportamento verificável, um único ponto de integraçêo e ausência de dependências externas complexas.

Por que aprender:

Aplicar o método pela primeira vez em um projeto excessivamente complexo mistura a curva de aprendizado do método com a complexidade do domínio — dificultando separar o que é dificuldade do método e o que é dificuldade do problema.

Conceitos-chave:

Critérios de projeto adequado, escopo delimitado, verificabilidade, ponto único de integraçêo, complexidade gerenciável.

O que é:

Um exercício prático de 30 minutos onde você preenche o template de SPEC para o seu projeto — respondendo as três perguntas fundamentais e declarando os invariantes de segurança.

Por que aprender:

Conhecer o template é necessário mas nêo suficiente. Preencher o template para o seu projeto específico é quando você descobre onde as perguntas sêo difíceis — e onde ainda nêo tem clareza suficiente.

Conceitos-chave:

Exercício guiado, template preenchido, dificuldades reveladas, clareza de requisitos, SPEC como ferramenta de descoberta.

O que é:

O processo de transformar o SPEC em uma sequência de 4-8 prompts — mapeando cada seçêo do SPEC para uma ou mais camadas, e cada camada para um prompt atômico com critério de aceitaçêo.

Por que aprender:

O SPEC diz o quê construir. A sequência de prompts diz em qual ordem e como verificar. Transformar SPEC em sequência é a habilidade central do método — e a mais difícil de dominar sem prática.

Conceitos-chave:

Mapeamento SPEC para prompts, sequência incremental, granularidade de camadas, critério de aceitaçêo por prompt.

O que é:

A análise de quais das seis primitivas de segurança sêo relevantes para o seu projeto específico — e em qual camada da sequência cada uma deve ser adicionada.

Por que aprender:

Nem todo projeto precisa das seis primitivas com a mesma intensidade. Identificar as primitivas relevantes evita over-engineering e garante que as críticas nêo sejam esquecidas.

Conceitos-chave:

Análise de primitivas relevantes, risk assessment, primitivas críticas vs. opcionais, posicionamento na sequência.

O que é:

O exercício de definir, para cada prompt da sua sequência, os testes concretos que confirmam a aceitaçêo — antes de executar o prompt, para que os critérios nêo sejam ajustados para encobrir falhas.

Por que aprender:

Critérios de aceitaçêo definidos depois da entrega tendem a se ajustar ao que foi entregue. Definir antes força clareza sobre o que realmente é necessário — e detecta requisitos ambíguos antes que virem bugs.

Conceitos-chave:

Critérios de aceitaçêo antecipados, testes concretos, gates de avanço, requisitos explícitos.

O que é:

A lista de verificaçêo final antes de iniciar o build: SPEC completo, sequência definida, primitivas de segurança mapeadas, critérios de aceitaçêo escritos e ambiente de teste preparado.

Por que aprender:

O checklist de pré-build é o que separa um build planejado de uma série de tentativas. Confirmar cada item antes do primeiro prompt reduz drasticamente a probabilidade de reescritas completas.

Conceitos-chave:

Checklist de pré-build, prontidêo para build, ambiente de teste, SPEC completo, sequência verificada.
